# ADR-001: Микросервисы вместо модульного монолита

**Статус:** Принято · **Дата:** 2026-10-18

## Контекст

Учебный проект системы переводов. Реальной нагрузки нет. Цель — отработать межсервисное взаимодействие, сагу, идемпотентность между сервисами и наблюдаемость.

## Ценность

Учёт денег отделён от часто меняющегося бизнес-процесса: новые типы переводов и лимиты выкатываются без риска сломать проводки, а сбой уведомлений не влияет на деньги клиента.

## Варианты

| | Модульный монолит | Микросервисы |
|---|---|---|
| Сложность | Низкая | Высокая: сеть, ретраи, распределённая согласованность |
| Транзакции | ACID на всё | ACID только внутри сервиса, между сервисами — сага |
| Независимые релизы и масштабирование | Нет | Да |
| Учебная ценность | Мало межсервисных задач | Все целевые темы |

## Решение

Микросервисы, **осознанно ради обучения**. Границы проведены по зонам ответственности: ledger (деньги, строгая согласованность), transfer (процесс, частые изменения), notification (может отставать).

## Последствия

- Нужны идемпотентность межсервисных вызовов, обработка таймаутов, сага.
- Больше инфраструктуры (отдельные БД, gRPC, Kafka).
- В продакшене с такой нагрузкой я бы начал с модульного монолита с теми же границами модулей и выделял сервисы по мере роста команды и нагрузки.

## Вопросы

1. Зачем микросервисы, если нагрузки нет? Не оверинжиниринг ли это?
2. По какому принципу вы провели границы сервисов?
