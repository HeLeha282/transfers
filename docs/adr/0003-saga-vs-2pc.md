# ADR-003: Сага вместо 2PC для переводов в другой банк

**Статус:** Принято · **Дата:** 2026-10-18

## Контекст

Перевод в другой банк затрагивает две системы: наш ledger и чужой банк (через СБП). Общей транзакции между ними нет. Внешняя система может ответить успехом, отказом или не ответить вовсе.

Внутренний перевод **не распределённый**: оба счёта в одной БД ledger, там обычная ACID-транзакция. Решение касается только внешних переводов.

## Ценность

При сбое или молчании чужого банка деньги клиента не теряются и не задваиваются: они либо доходят, либо возвращаются, а клиент всё это время видит понятный статус.

## Варианты

| | 2PC (двухфазный коммит) | Сага (оркестрация) |
|---|---|---|
| Как работает | Координатор: «готовы?» → все держат блокировки → «коммит» | Цепочка локальных транзакций, при отказе — компенсации |
| Согласованность | Строгая, атомарная | Итоговая, промежуточные состояния видны (`RESERVED`, `SENT`) |
| Можно ли с чужим банком | ❌ Чужой банк не участвует в нашем протоколе prepare/commit | ✅ Нужна только идемпотентная отправка по нашему идентификатору перевода |
| Падение координатора | Участники застревают с блокировками до его возвращения (протокол блокирующий) | Состояние в БД; другой под или recovery-воркер продолжает с последнего статуса |
| Сложность | Нужна поддержка всеми участниками | Компенсации, идемпотентность каждого шага |

Отдельно: оркестрация vs хореография. Выбрана оркестрация (transfer-service управляет шагами): процесс виден в одном месте, проще статусы и отладка. Хореография (сервисы реагируют на события друг друга) лучше при многих независимых участниках, но процесс размазан по сервисам.

## Решение

Сага с оркестрацией в transfer-service. Шаги «резерв → подтверждение или отмена» по сути паттерн **TCC (Try–Confirm–Cancel)**: резерв гарантирует, что деньги будут на месте к моменту подтверждения.

Статус `SENT` записывается до вызова чужого банка. При таймауте холд не снимается вслепую: статус остаётся `SENT`, recovery-воркер повторно отправляет тот же запрос с тем же `transfer_id` до точного ответа. Чужой банк по `transfer_id` отсекает дубли, поэтому повтор не создаёт второй перевод.

## Последствия

- Каждый шаг идемпотентен: в ledger — по паре «перевод + тип операции» ([ADR-005](0005-idempotency.md)), в запросе к чужому банку — по `transfer_id`.
- Требование к внешней системе: дедупликация запросов по `transfer_id`.
- Нужен recovery-воркер с lease, чтобы зависшие переводы доводил ровно один под.
- Клиент видит промежуточный статус «в обработке», это продуктовое следствие итоговой согласованности.

## Вопросы

1. Почему не 2PC? Что будет, если координатор 2PC упадёт между фазами?
2. Что вы делаете, если чужой банк не ответил? Почему нельзя сразу вернуть деньги?
