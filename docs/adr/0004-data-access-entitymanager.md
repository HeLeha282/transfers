# ADR-004: Доступ к данным в ledger через EntityManager и свои запросы

**Статус:** Принято · **Дата:** 2026-10-18

## Контекст

Ledger меняет деньги: каждое списание — блокировка строки счёта, обновление баланса и вставка проводок в одной транзакции. Ошибка в любом запросе означает потерянные или задвоенные деньги. Нужно выбрать способ работы с БД.

## Ценность

Запросы, которые меняют деньги, написаны явно и видны на код-ревью, а не генерируются из имён методов. Это снижает риск тихих ошибок, а при инциденте быстрее понять, какой запрос что сделал.

## Варианты

| | Spring Data JPA (репозитории) | EntityManager + свои JPQL/native-запросы | JdbcClient / JdbcTemplate |
|---|---|---|---|
| Кто пишет запросы | Генерируются из имён методов | Разработчик | Разработчик |
| Неявное поведение | Dirty checking, кеш первого уровня, генерация SQL | Dirty checking и кеш первого уровня остаются для загруженных entity | Нет |
| Блокировки | `@Lock` на методе репозитория | `LockModeType.PESSIMISTIC_WRITE` в `em.find` / `setLockMode` или `FOR UPDATE` в native | `FOR UPDATE` в тексте |
| Учебная ценность | Средняя | Высокая: Hibernate + понимание его механизмов | Высокая для SQL, Hibernate не изучается |

## Решение

**EntityManager + свои JPQL и native-запросы**, транзакции через `@Transactional`. Репозитории Spring Data не используем, чтобы каждый запрос был написан явно. Схема — миграциями Liquibase; Hibernate только проверяет соответствие сущностей таблицам (`ddl-auto: validate`) и не меняет схему.

Причина выбора Hibernate, а не JDBC: хочу на практике разобраться в Hibernate и его механизмах, которые используются в большинстве Java-проектов, сохранив контроль над запросами.

## Последствия и риски

Загруженные через EntityManager сущности отслеживаются Hibernate, поэтому важно учитывать его неявное поведение:

- **Dirty checking.** Любое изменение поля загруженной сущности уходит в `UPDATE` при коммите, даже без явного сохранения. Правило: сущности счетов меняются только в сервисном методе перевода.
- **Запись всей строки и lost update.** По умолчанию Hibernate обновляет все колонки, включая неизменённые. Если между чтением и коммитом строку изменила другая транзакция, её изменение будет затёрто. Правило: счёт, который будет изменён, загружается сразу с блокировкой — `em.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE)` (в БД `SELECT ... FOR UPDATE`).
- **Кеш первого уровня.** Загруженный объект хранится в памяти до конца транзакции; после native-`UPDATE` он не обновляется сам и содержит устаревшие значения. Правило: для одной сущности не смешивать изменения через объект и через запрос, а если смешали — `em.refresh()`.
- **Контроль SQL.** В dev включено логирование запросов (`logging.level.org.hibernate.SQL=DEBUG`), чтобы видеть, какие запросы Hibernate реально отправляет.

Аннотация `@Lock` не используется: она относится к репозиториям Spring Data, а запросы пишутся через EntityManager. Блокировка задаётся через `LockModeType` в `em.find` / `setLockMode` или `FOR UPDATE` в native-запросе.

Темы для изучения: состояния сущности (transient / managed / detached / removed), `persist` и `merge`, flush и его режимы, lazy loading и N+1, `@Version`, `@DynamicUpdate`.
