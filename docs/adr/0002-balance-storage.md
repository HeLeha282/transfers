# ADR-002: Хранение баланса

**Статус:** Принято · **Дата:** 2026-10-18

## Контекст

Ledger должен быстро проверять доступный остаток при списании, корректно работать при параллельных списаниях с одного счёта и позволять восстановить историю любого счёта.

## Ценность

Клиенту и поддержке всегда можно показать, из каких операций сложился баланс; банк может проверить, что деньги не появились и не исчезли, а ошибка исправляется видимой обратной проводкой, а не тихой правкой.

## Варианты

| | А. Только проводки, баланс = SUM | Б. Только баланс в `accounts` | В. Проводки + баланс в одной транзакции |
|---|---|---|---|
| История, аудит, сторно | ✅ | ❌ | ✅ |
| Сверка (сумма = 0) | ✅ | ❌ | ✅ |
| Скорость проверки баланса | ❌ SUM по растущей таблице | ✅ | ✅ |
| Точка блокировки при списании | Всё равно нужна строка счёта (новые проводки нельзя заблокировать заранее) | Строка счёта | Строка счёта |
| Риск | — | Баг необратимо портит деньги | Баланс может разойтись с проводками при баге |

## Решение

**Вариант В:** неизменяемый журнал `entries` + `balance` в `accounts`, обновляемые в одной транзакции. Блокируется строка счёта.

`balance` денормализован: его можно вычислить как сумму проводок счёта, но он хранится отдельно, чтобы не считать сумму при каждом списании. Так же устроен `reserved`: каждый холд хранится отдельной строкой в `holds`, а `reserved` на счёте — сумма активных холдов. Отдельные строки нужны, чтобы при подтверждении или отмене перевода знать, какую именно сумму списать или освободить, в том числе после сбоя.

## Последствия

- Каждое списание = обновление двух строк `accounts` + две вставки в `entries` в одной транзакции.
- Каждая проводка ссылается на операцию, которая её создала (`entries.operation_id` → `operations`): по любой проводке видно, откуда она взялась, а без зарегистрированной операции проводку создать нельзя.
- Баланс — производное значение, источник правды — журнал проводок. Риск расхождения закрывается на трёх уровнях:
  - **предотвращение:** `balance` меняется только вместе с проводками, в одной транзакции и в одном месте кода;
  - **обнаружение:** сверка `accounts.balance = SUM(entries.amount)` по каждому счёту (в тестах и периодически), при расхождении — оповещение;
  - **исправление:** баланс пересчитывается по проводкам; ошибочная проводка исправляется сторно.
- Горячий счёт (много операций в секунду на одну строку) станет узким местом — разбираем на этапе 6.

## Вопросы

1. Почему не хранить только баланс? Почему не считать его через SUM?
2. Что будет с горячим счётом, например счётом крупного маркетплейса, на который идут тысячи зачислений в секунду?
